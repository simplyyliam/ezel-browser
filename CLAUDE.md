# Ezel

A lightweight browser for designers.

## Stack
- Tauri v2 (Rust) with the `unstable` feature for multi-webview, using the system webview
- UI: React + Vite + shadcn + Tailwind v4 (`src/`)
- UI primitives are Base UI, never Radix. Don't add @radix-ui/* packages. (shadcn style `base-luma` in `components.json`; compose with `render`, not `asChild`.)
- Rust side: `src-tauri/`

## Run
`npm run tauri dev`

## Releasing
1. `/release` (`.claude/commands/release.md`, optional notes: `/release "known issue: …"`): on a clean `main`, runs every check, picks the version, bumps it in `tauri.conf.json`, `Cargo.toml`, `package.json` and `package-lock.json`, adds the `CHANGELOG.md` section and an annotated `vX.Y.Z` tag. Never pushes.
2. Test the app.
3. `npm run release` (`scripts/release.sh`, Git Bash): checks main, the tag and the versions again, shows what goes out, asks, then pushes `main` and that one tag. Never forces, never pushes other tags.
4. The tag runs `.github/workflows/release.yml`: NSIS and MSI installers in a draft release "Ezel X.Y.Z" (not a pre-release: the updater reads `releases/latest`), its notes from the changelog, plus the signed update bundles and `latest.json` (`--config src-tauri/tauri.release.conf.json`, repository secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`). Publish the draft on GitHub; installed Ezel finds it within a day. The installers aren't code-signed (SmartScreen warns; the notes say how to get past it); the updater key is a separate, free signature.

### Auto-updates (`src-tauri/src/updater.rs`)
Tauri's updater plugin, release builds only (never in `perf` builds). A thread checks `plugins.updater.endpoints` (GitHub's latest release `latest.json`) 20s after launch and then once a day, skipped while an update waits; a newer version downloads quietly and is verified against `plugins.updater.pubkey`. `update-status` tells the UI; the sidebar footer shows "Update ready" (`features/app-sidebar/update-note`) and only its click installs (`install_update`: saves the session, the NSIS installer closes and reopens Ezel). The plugin's own JS commands are never granted. Errors are logged by kind, never with URLs. Debug builds: `EZEL_UPDATE_MOCK=1` pretends 9.9.9 is ready (a click just restarts).

## Architecture
The frontend owns content geometry; Rust follows the reported bounds. The UI only sends commands and listens to events.

One frameless window (`main`, `decorations(false)`):
- `ui`: the React app, covers the whole window (Rust re-applies full-window bounds on every resize). It draws its own titlebar, window controls and drag region.
- `tab-<id>`: one webview per **loaded** tab (`src-tauri/src/browser/`). Only the shown tab is visible, placed wherever the frontend reports via `set_content_bounds`; the "content" commands below always apply to it. Hidden until `set_content_visible(true)`, and a newly created one also until its page starts rendering (`browser::reveal` on its first load start, or after `REVEAL_FALLBACK`, 1.5s), so it never flashes WebView2's white default background. Tab webviews are created at the page's current bounds (`content::current_bounds`; at launch, before the UI reports any, the window inset by the frame's 6px padding: `content::assume_bounds` in `build_window`), never 0x0: one resized on show drew part white, part black.

Only `ui` has IPC; tab webviews have none (the only capability is scoped to the `ui` label and the app's own origin; `websites_in_tabs_cannot_reach_ipc` in `lib.rs` guards it). Tabs load only `http`, `https` and `about:blank` (`browser/url_policy.rs`): typed input refuses `file:`, `javascript:`, `data:` and other `about:` pages, and every navigation, new window, restored session and pinned URL is checked against the same rule. All use WebView2's Fluent overlay scrollbars and the same `BROWSER_ARGS` (they share a data directory and one WebView2 environment, so these must match).
Ezel's UI has a strict Content Security Policy (`tauri.conf.json` `app.security.csp`, table and reasons in `docs/security-review.md`): only its own scripts (plus Tauri's hash of the inline theme script), styles with `'unsafe-inline'` (the theme store's runtime `<style>`; Tauri may not touch `style-src`: `dangerousDisableAssetCspModification`), bundled fonts, images from anywhere (favicons), IPC. A new UI need (a remote font, a worker, an iframe) needs a CSP change and its reason in that table. SmartScreen stays on (never add `msSmartScreenProtection` back to `BROWSER_ARGS`). A page may open its own `blob:` (`url_policy::is_allowed_from_page`), never typed or saved.
Quiet defaults (`docs/design/decisions.md`, "Quiet defaults"): no password saving or autofill, notification requests denied without a prompt, no autoplay with sound before the page is used.

### Tabs backend (`src-tauri/src/browser/`)
Studied from Zen (workspaces, pinned tabs, folders, essentials, session store) and Arc (spaces, pinned/today tabs, favorites); see `docs/design/decisions.md`, "Tabs, folders and spaces".
- `model.rs`: pure data + rules, no Tauri. Operations return `Effect`s (show / destroy / navigate) that `mod.rs` applies to webviews. Unit-tested (`cargo test`).
- Spaces each hold `pinned` items (tabs and one-level folders) and `temp` tabs (newest first), and remember their own shown tab. Swatches: 8 global slots shared by every space.
- Memory (see Performance): a webview exists only for loaded tabs. Restored tabs stay unloaded until selected; at most `MAX_LOADED_TABS` (5) stay loaded, least recently used unloaded first; background tabs idle `IDLE_UNLOAD_MS` (5 min) are unloaded (checked every 15s); background tabs hidden `SUSPEND_AFTER_MS` (30s) are frozen with WebView2 `TrySuspend` and resumed when shown; tabs playing audio and dev tabs (`is_dev_url`: `localhost`, `127.0.0.1`, `[::1]`, `*.localhost`, any port) are never auto-unloaded or frozen (only by hand); hidden webviews get WebView2's low memory target.
- Persistence (`store.rs`): `<app data>/ezel/session.json`, debounced 1s, atomic write with a `.bak` fallback, flushed on exit. Unreadable files are moved aside, never overwritten.
- Threading: commands that may load a tab are `async` (creating a webview from the main thread's sync command/event handlers deadlocks on Windows). Never hold the model lock while calling a webview API.

### Page layers (the inject path)
The one way Ezel changes how a website looks: a **named CSS layer** injected into the shown tab (`browser/layers.rs`, pure and tested). Lenses use it now; Loupe, Palette Pull and later tools reuse it (add a `PageLayer` variant, or a sibling for scripts, following the same rules).
- A layer is a `PageLayer` variant with fixed CSS in Rust. The UI only names it (`toggle_page_layer`); serde rejects any other value. Never build CSS or JS from page content or UI strings.
- Applied by `eval`ing `apply_script()` (an IIFE: top frame only, adds/refreshes `<style id="ezel-layer-<name>">` under `<html>`, waits for `<html>` with a MutationObserver at the start of a load, defines no globals, sends nothing back); removed by `remove_script()`. Tab webviews have no IPC, so a page can't reach the app through it.
- State: `Live.layers` (model). Re-applied on every page event that starts or finishes a load (`on_page_event`: Tauri's "started" is WebView2's `ContentLoading`, when the new document exists), so a layer stays on across navigations in its tab. Same-document navigations keep the element.
- Per tab: activating another tab (or a space with none) turns the previous tab's layers off (`drop_layers_except`); coming back, they're off until toggled again. An unloaded tab's layers go with its webview.
- Lenses stack: each sets a custom property (`--ezel-lens-<name>`) and one shared rule composes them into `html { filter }`.

### Page menu (`browser/page_menu.rs`, `features/browser-view/page-menu`)
Right-clicks in a page open Ezel's own menu (WebView2's documented custom menu): Rust handles `ContextMenuRequested` with a deferral (kept on the main thread, `webview2::on_context_menu`), decides the entries from the target (link, image, editable text, selection, the page; Inspect last; native entries only when WebView2 offers them), moves focus to the UI and emits `page-menu`. The UI draws a Base UI menu at the point (cut out of the page like every popup) and answers once with `choose_page_menu_item`. WebView2's own commands (copy, paste, save image, inspect…) run on what was right-clicked (`SelectedCommandId`, focus back to the page first); Ezel's (Open Link in New Tab: a temp tab on top, unloaded until opened; Copy Link; Search for "…": a new tab) use the link, image or selection Rust kept, never UI text. A new right-click finishes the previous menu.

## Performance
Ezel's promise is "light": measured, not guessed. Study and numbers: `docs/perf/baseline.md` (method, findings) and `docs/perf/results.md` (before/after, what helped, what was reverted).
- **Measure**: release builds only. `npx tauri build --no-bundle --features perf` (`npm run tauri` is `tauri dev`), then `powershell -ExecutionPolicy Bypass -File scripts/measure-memory.ps1` (scenarios `launched`, `ui-only`, `1tab`, `5tabs`, `10tabs`, `idle5min`; `-Exe` to compare saved binaries, `-SettleSeconds`, `-Runs`). It sums the whole process tree (app + every WebView2 process) as private working set (Task Manager's number) and private bytes, median of samples. Sites vary day to day: compare builds in the same session, alternating runs.
- **The `perf` cargo feature** (measurement only, never in normal builds): `EZEL_PERF_URLS` opens tabs at startup (`""` first-run tab, `none` no tabs, or comma-separated http(s) URLs) in a throwaway session (`<app data>/ezel-perf`), so measurements never touch the real session (`browser/perf.rs`).
- **Numbers** (2026-10-21, `docs/perf/results.md`), private working set, before → after this work: just launched 202 → 200 MB, UI only 109 → 112 MB, 1 tab 148 → 151 MB, 5 tabs 217 MB both, 10 tabs 734 → 665 MB (−9%; private bytes −11%), after 5 min idle 602 → 480 MB (−20%; private bytes −34%, 15 → 8 processes).
- **Rules for every feature**:
  - No polling and no timers while idle. Anything periodic runs only while its UI is visible (the load meter polls only while the sidebar shows) and stops when hidden. Animations run only during an interaction; nothing loops forever (`requestAnimationFrame` loops end when the motion ends).
  - Tabs unload by default: never keep a webview alive for a feature's convenience. A new "keep this tab alive" exemption (like audio or dev tabs) needs a measured reason.
  - One WebView2 environment: every webview shares the data directory and `BROWSER_ARGS`. Never give a webview its own data folder or arguments (that starts a second browser process, ~60 MB).
  - Background work in tabs (injected scripts, layers) stays out of hidden tabs, which are frozen after 30s anyway.
  - A change that claims to save memory shows it with `scripts/measure-memory.ps1`, before and after, in the same session.

## Bindings
`src/shared/bindings.ts` is generated by tauri-specta from the Rust commands, events and types (same setup as Foundry; see `docs/design/decisions.md`, "Typed bindings"). Never edit it by hand.
- Regenerated by running the app in debug (`npm run tauri dev`) or by `cargo test` (in `src-tauri/`).
- A new command must be added to the `collect_commands!` list in `specta_builder()` (`src-tauri/src/lib.rs`), a new event (a `#[derive(Type, Event)]` payload with `#[tauri_specta(event_name = "…")]`) to `collect_events!`. Every type that crosses the boundary derives `specta::Type`, with camelCase fields.
- Commands return `Result<T, AppError>` (`src-tauri/src/error.rs`): `{ code, message }`, `code` a stable snake_case `ErrorCode`. In TS every command resolves to `{ status: "ok", data } | { status: "error", error }`.
- Events are emitted with `emit_to_ui` (typed, to the `ui` webview only).

## Contract (UI ↔ Rust)
New commands must also be allow-listed in `src-tauri/build.rs` (app manifest) and `src-tauri/capabilities/default.json` (`allow-<name>`), otherwise every call is rejected silently, and added to `collect_commands!` (see Bindings).

Commands (`invoke`):
- `navigate(input: string)`: loads in the shown tab (a new temp tab if none is shown). A web URL is loaded (`https://` added if missing); `file:`, `javascript:`, `data:`, `vbscript:`, `blob:` and `about:` pages other than `about:blank` are refused (`invalid_input`); anything else is searched on Google (`SEARCH_URL`). `open_tab(input)` resolves input the same way.
- `go_back()`, `go_forward()`, `reload()`: the shown tab. `reload_tab(id)`: any loaded tab (a menu's Reload Tab); an unloaded one is left alone
- `hard_reload()` (bypasses the cache, through the DevTools protocol), `stop_loading()`, `open_devtools()` (its own window; tab webviews are built with `devtools(true)`, release included): the shown tab. Windows only for now (`unsupported` elsewhere, except reload/stop fallbacks).
- `get_memory()` → `MemoryReport { totalMb, sharedMb, tabs: { id, mb, approximate }[] }`: the load meter. Every WebView2 process plus Ezel's own (private bytes), split over the loaded tabs by the frames each renders (`browser/memory.rs`, tested; `docs/research/memory-meter.md`). Shared renderers are split evenly (`approximate`); processes serving no tab are `sharedMb`. Unloaded tabs aren't listed (the UI calls them resting). Async; one reading at a time; any failure (WebView2 not answering, a timeout, a reading already running) is `unavailable`. The readout keeps the last good reading through failures and hides only after 15s without one (counted while polling). Windows only (`unsupported` elsewhere). WebView2's frame-info iterator doesn't keep its collection alive: hold the collection while iterating (a dropped one crashed the app).
- `toggle_page_layer(layer: "squint" | "greyscale")` → on: toggles a page layer (lens) in the shown tab (see Page layers). `no_tab_shown` without one.
- `clear_site_data()` → host: everything the shown page's site stored (CDP `Storage.clearDataForOrigin`, origin built in Rust from the tab's URL: `browser/site.rs`), then it reloads. `invalid_input` for a page that isn't a website.
- `find_start(query)`, `find_next(backward)`, `find_stop(refocus)`: find in page in the shown tab (WebView2's `ICoreWebView2Find`, 1.0.2849+, its own find dialog suppressed; `unsupported` on older runtimes). Queries: one line, at most 1000 characters (`invalid_input`); an empty one ends the session. Results come as `find-changed`.
- Downloads (`browser/downloads.rs`, WebView2 `DownloadStarting` handled so its flyout never shows): `get_downloads()` → `{ downloads: { id, fileName, state: "inProgress" | "completed" | "cancelled" | "failed", receivedBytes, totalBytes | null }[] }` (newest first, this session only, at most 50), `open_download(id)` (completed and on disk; Explorer opens it with its default app), `show_download_in_folder(id)`, `cancel_download(id)`, `clear_downloads()` (forgets finished ones; files stay). Files go where WebView2 saves them: the Windows Downloads folder unless the page's Save As picked another. The UI gets file names only; paths stay in Rust and are never logged.
- Site permissions (`browser/permissions.rs`): `answer_permission(id, allow | null)` (Ezel's prompt: true/false is remembered for the site, null declines once), `get_site_permissions()` → `{ origin, host, permissions: [kind, "allow" | "deny"][] }[]`, `revoke_site_permission(origin, kind)` (it asks again). Kinds: `camera`, `microphone`, `location`, `clipboard` (reading). WebView2 `PermissionRequested` (`webview2::quiet_defaults`): notifications always declined; those four answered from Ezel's memory, else (shown tab only, others declined) deferred while `permission-asked` opens the prompt; never saved in WebView2's profile. Stored in `<app data>/ezel/permissions.json` (atomic write, unreadable file moved aside). Other kinds, and every kind in sign-in popups, keep WebView2's prompt.
- `copy_page_url()` → the shown tab's URL, written to the OS clipboard by Rust (Win32), because a shortcut pressed in the website leaves focus there and the UI's `navigator.clipboard` can't write without focus. `no_tab_shown` when none is.
- `get_page()`: the shown tab's page (`page-changed` shape), so the UI can catch up on mount
- `choose_page_menu_item(id, action | null)`: the website's right-click menu (see Page menu). Only an offered, enabled action of the open menu `id` runs (`invalid_input` otherwise); a stale id is ignored.
- `set_content_bounds(x: number, y: number, width: number, height: number)`: places the content webview; logical px relative to the window's top-left
- `set_content_radius(radii: [number, number, number, number])`: clips the content webview to rounded corners; logical px, CSS order (top-left, top-right, bottom-right, bottom-left). Windows only for now.
- `set_content_cutout(id: string, rect: [x, y, width, height] | null, radius: number)`: cuts a window-relative rounded rect (logical px) out of the content webview's clip region under `id`, so the UI below shows through without moving or resizing the page. `rect: null` clears that id. Holes: `"titlebar"`, `"sidebar"`. Use `useContentCutout` (`shared/content-cutout.ts`), which follows an element every frame while it moves. A hole shows Ezel's own background (near-black in dark mode), never the page, so the hook cuts only what the element covers: nothing while it fades in or out (opacity below 1, itself or an ancestor), and while it moves only what it covers from what the screen still shows (a few frames back, more when frames come slowly) until the hole lands (the measured call lag): its animations are sampled at those times, so no ghost trails or leads it. Anything that slides over the page should be its own GPU layer (`will-change-transform`, like the collapsed sidebar card): repainted every frame, it falls behind its hole after a launch or a restore. Windows only for now.
- `set_content_visible(visible: boolean)`: shows or hides the content webview. It starts hidden, so report bounds first, then show it.
- `set_forwarded_hotkeys(hotkeys: { id, key, ctrl, shift, alt, focusUi, whileLoading }[])`: replaces the shortcuts Rust catches in the tab webviews (see Hotkeys). `key`: `a`–`z`, `0`–`9`, `f1`–`f12`, `tab`, `escape`, `left`, `right` (anything else: `invalid_input`). Several entries may share an id (alternate keys). `whileLoading`: caught only while the shown tab loads, otherwise the page gets the key (Esc). Empty until first called: nothing is caught.
- `get_update_status()` → `{ readyVersion: string | null }`; `install_update()`: installs the downloaded update and restarts (`not_found` when none is ready). See Auto-updates.
- `get_window_radius()` → `{ radius: number | null, customized: boolean }`: the corner radius Windows 11 actually draws for the window, logical px. Without the Windhawk "Custom Window Corner Radius" mod: 8, or 0 when fullscreen/maximized/snapped. With it (`customized: true`): the mod's radius, or 0 where it leaves windows square. `radius: null` = unknown (not Windows): keep the UI's default radii. The UI sets `--radius-frame` to `radius − 4` (frame padding).

Tab commands (ids are numbers; every change also emits `tabs-changed`):
- `get_tabs()` → `TabsState`: `{ activeSpaceId, activeTabId | null, closedCount, recentlyClosed: { url, title | null, favicon | null }[] (the last 5, newest first), swatches: (TabView | null)[8], spaces: { id, name, icon, items: ({kind:"tab", tab} | {kind:"folder", folder:{ id, name, collapsed, tabs }})[], tempTabs }[] }`. `TabView`: `{ id, url, title | null, favicon | null, pinnedUrl | null, isLoaded, isLoading, isPlayingAudio, isMuted, isDev, layers }`. `icon` is a lucide icon name.
- `open_tab(input?: string)` → id: new temp tab on top of the active space, selected (home page without input). Links opened in a new window (`target=_blank`) do the same; sized popups (OAuth) open in a small window of Ezel's own (`browser/popup.rs`, label `popup-<n>`, no IPC, same environment so `window.opener` works) titled with its domain first (`site::popup_title`); `window.close()` closes it.
- `cycle_tab(backward)`: Ctrl+Tab / Ctrl+Shift+Tab. The active space's next tab in most-recently-used order (`model.rs`, `CYCLE_WINDOW_MS`): presses within 1.2s walk deeper into one frozen order (Ctrl "held"; the website's key-ups never reach us), after a pause it returns to the previous tab. Swatches aren't in the walk, but a shown swatch starts it.
- `reopen_closed_tab()` → id | null: Ctrl+Shift+T. Pops the closed-tab stack (`session.closed`, newest last, max `MAX_CLOSED_TABS` = 25, persisted in session.json) and puts the tab back in its space, folder or swatch slot at its old index (clamped to the end); a folder that's gone → the end of its space's pinned list, a space that's gone → the active space, a full swatch grid → top of the active space's temp tabs. Selected. A tab goes on the stack when it's removed (temp close, `remove_tab`, trash-all, top tab reopened first); closing a pinned tab or swatch only unloads it, so it doesn't.
- `reopen_recent_tab(n)` → id: the n-th most recently closed tab (0 = newest), back where it was, selected (the palette's chips; `invalid_input` past the end).
- `activate_tab(id)`; `close_tab(id)`: a temp tab is removed, a pinned/swatch tab is unloaded and reset to its pinned URL; `remove_tab(id)`: removes any tab; `unload_tab(id)`: frees memory, keeps the page.
- `move_tab(id, to)`: pin/unpin, swatch, folder, reorder, other space. `to`: `{kind:"swatch", slot}` (occupied: swap) | `{kind:"pinned", spaceId, folderId: id | null, index: number | null}` (null = end) | `{kind:"temp", spaceId, index: number | null}` (null = top). Pinned/swatch tabs remember a `pinnedUrl`; temp tabs forget it.
- `set_tab_muted(id, muted)`: WebView2 `IsMuted`. Stored on the tab (`muted`, persisted) and re-applied whenever its webview is created, so unloading never un-mutes it. Windows only for now.
- `reset_tab(id)`: back to its pinned URL; `update_pinned_url(id)`: current URL becomes the pinned URL; `clear_temp_tabs(spaceId)`: trash-all.
- Folders: `create_folder(spaceId, name, index?)` → id, `create_folder_with_tab(tabId, name)` → id ("New Folder with Tab": a top-level pinned tab is replaced by the folder; a temp tab's or swatch's folder goes at the end of the pinned list; a tab in a folder gets one right after it: no nesting), `rename_folder(id, name)` (names: trimmed, 1–60 chars, one line, else `invalid_input`), `set_folder_collapsed(id, collapsed)`, `move_folder(id, spaceId, index?)`, `delete_folder(id, keepTabs)` (`keepTabs`: unpack; otherwise its tabs go on the closed-tab stack), `unload_folder(id)`.
- Spaces: `create_space(name, icon)` → id, `update_space(id, name?, icon?)`, `move_space(id, index)`, `delete_space(id, moveTo?)` (not the last one; `moveTo`: its folders and tabs go to the end of that space's lists and the shown tab stays on screen, otherwise they close onto the closed-tab stack), `switch_space(id)` (shows the tab it showed last).

Window APIs (`@tauri-apps/api/window`): `minimize`, `toggleMaximize`, `close`, `startDragging`, `isMaximized`, `isFullscreen`, `cursorPosition`, `innerPosition`, `innerSize`, `scaleFactor` (the last four let the titlebar peek follow the cursor above the window).

Event emitted to the `ui` webview:
- `page-changed`: `{ url: string, title: string | null, canGoBack: boolean, canGoForward: boolean, isLoading: boolean, security: "none" | "secure" | "notSecure" | "certificateError", fullscreen: boolean, error: null | "offline" | "notFound" | "cantConnect" | "timedOut" | "certificate" | "crashed" }` (`browser/site.rs`: the scheme, plus WebView2's `ServerCertificateErrorDetected` for the page's own host, cleared by each navigation)
  The shown tab's page. Emitted on navigation start, on page load finish, when the document title changes, and when another tab is shown (all empty/false when none is).
- `tabs-changed`: `TabsState` (as `get_tabs`). Emitted after every tab/folder/space change.
- `tab-updated`: one `TabView`. A tab's URL, title, favicon, loading or audio state changed (any tab, shown or not).
- `hotkey-pressed`: `{ id: string }`. A shortcut from `set_forwarded_hotkeys` was pressed while the website had focus. Rust catches it on each tab webview (WebView2 `AcceleratorKeyPressed`) because those keys never reach the `ui` webview; the page doesn't receive it. With `focusUi` it moves keyboard focus to `ui` first. Auto-repeat is swallowed but not re-emitted. Windows only for now.
- `update-status`: same payload as `get_update_status`, when it changes.
- `downloads-changed`: same payload as `get_downloads` (progress at most every 250ms per download).
- `permission-asked`: `{ id, tabId, host, permission }`: a site asks; the titlebar peek opens with Ezel's prompt (showing another tab declines it once).
- `link-status`: `{ text }`: the shown page's status text (a hovered link's address, at most 300 characters; "" when none or another tab is shown). WebView2's own status bubble is off (`IsStatusBarEnabled`); `features/browser-view/link-status` draws a pill at the page's bottom-left, only the domain strong, cut out of the page.
- `find-changed`: `{ active, count }` (active 1-based, 0 for none): the shown tab's find results.
- `page-menu`: `{ id, x, y, groups: { action, enabled }[][], selection | null }`: open Ezel's page menu at that window point (logical px).
- `window-radius-changed`: same payload as `get_window_radius`. Emitted only when the value changes (window resize/maximize/snap/fullscreen, or the mod's registry settings change).

## Frontend structure
```
src/
  widgets/<widget>/              parent: lays out and composes its features
  features/<widget>/<feature>/   features belong to the widget folder with the EXACT same name
  shared/                        Tauri invoke/listen helpers, contract types (PageChanged)
  theme/                         theme provider/store (light/dark/system + runtime token overrides)
  components/ui/                 shadcn components
```
- Features never import from widgets or from other features. Code two features need goes in `shared/`. `theme/` is app-wide like `shared/`: anything may import it.
- Widgets may import from their own features and from `shared/`.
- Current widgets:
  - `widgets/app-titlebar` composes `features/app-titlebar/{quick-tabs,site-identity,window-controls}`. It's a Zen-style peek (studied from Zen's source, see `docs/design/decisions.md`): it overlays the top of the window, opens from a 4px strip at the top edge, grows its height over 150ms ease-in-out and never moves the page. The website is a native webview above the UI, so the bar is cut out of it with `useContentCutout` and Rust cuts it out of the page. No shadow. Left: the shown tab's folder's other tabs as icons (outside a folder, the Swatches); middle: the site's host with a lock (open lock for HTTP, a warning for certificate problems), only the registrable domain emphasised (`shared/site.ts`, `splitHost`); right: the window controls. Clicking the domain opens the site info panel inside the bar (the bar grows, so it's cut out with it; it keeps the bar open until Esc, a press elsewhere or the UI losing focus): connection status, this site's remembered permissions (each can be forgotten), "All Site Permissions…" and "Clear This Site's Data…" (asks once, in place). A permission request opens the bar by itself with a card under the domain: "<domain> wants to use your camera", Don't Allow / Allow (Esc: declined once).
  - `widgets/browser-view` composes `features/browser-view/{content-slot,find-bar,page-menu}`: the placeholder the content webview is placed over, the find bar (Ctrl+F: a small bar in the page's top-right corner, cut out of the page with `useContentCutout("find")`; Enter / Shift+Enter, Esc closes and gives the page focus back; showing another tab closes it) and the page menu
  - `widgets/app-sidebar` composes `features/app-sidebar/*` (see Sidebar below)
  - `widgets/site-permissions` composes `features/site-permissions/site-list`: every site's remembered permissions to review and forget (a dialog without a backdrop, from the site panel's "All Site Permissions…" or the palette's Site Permissions). Mounted in `AppLayout`.
  - `widgets/command-palette` composes `features/command-palette/{search-field,results,footer}` (see Command palette below). Mounted in `AppLayout`.

## Sidebar
Built from `docs/design/sidebar-1.png` (a 1.5x export) with shadcn's `Sidebar` (`collapsible="offcanvas"`, collapsed by default). The variant follows the state: docked (open) uses `variant="sidebar"` (flat: no padding, radius, ring, shadow or divider), collapsed/peeking uses `variant="floating"` (Zen's card).
- Behaves like Zen's compact mode in its "Only Sidebar" layout (studied from Zen's source, see `docs/design/decisions.md`, "Sidebar peek"). **Collapsed**: the page is full width; hovering the window's left edge (the frame's 4px padding) peeks the card out over the page: in 0.25s on Zen's spring curve (`ease-zen-peek`), out 0.15s ease. It stays while hovered, focused or showing a menu, 150ms after the pointer leaves, and while the pointer is within 200px left of the window. **Open** (Ctrl+B / `SidebarTrigger`): docked beside the page. Logic: `widgets/app-sidebar/use-sidebar-peek.ts`. The card (plus its 1px ring) is cut out of the website so it shows above it; the floating shadow is clipped over the page.
- Layout: `AppLayout` = `SidebarProvider` > `WindowFrame` (titlebar on top) > row (`relative`) > `AppSidebar` + `SidebarInset` > `<Outlet />`. The provider wraps the frame so the titlebar can use `useSidebar`. The browser page renders only the `BrowserView` (ContentSlot).
- Positioning: the sidebar is `absolute h-full` against the row below the titlebar, not shadcn's viewport-fixed default (overridden through `className`).
- **shadcn components in `components/ui/` stay at registry defaults. Never edit them**; customise at the call site with `className`/`render`. Build sidebar UI from its primitives (`SidebarGroup`, `SidebarMenu`, `SidebarMenuItem`, `SidebarMenuButton`, `SidebarMenuSub*`, `SidebarInput`, `SidebarSeparator`, `SidebarTrigger`) instead of raw buttons.
- Width: `SIDEBAR_WIDTH` (244px) in `widgets/app-sidebar`, set via `--sidebar-width`; groups keep shadcn's `p-2`; the swatch grid is left-aligned, 3px gaps, 27px high: fewer than 4 swatches share the full width, from 4 on they're 45px cells (`SWATCH_GRID`, `swatchColumns`). The design image is scaled up for legibility; sizes are in `docs/design/decisions.md` (Sizing).
- Padding/corners: no padding in either state (`p-0`): the frame's `p-1` is the only gap, and the sidebar runs to the top, bottom and left of the browser area. The peeking card takes the frame radius (`rounded-frame`) and keeps only its 1px ring. The inset uses `rounded-frame`, with square left corners while docked (flush with the sidebar); the ContentSlot inherits the inset's corners and passes them to the website clip.
- Toggle: **Ctrl+B** from anywhere: shadcn's shortcut while the UI has focus, and the `toggleSidebar` hotkey (`useHotkey`, forwarded by Rust) while the website has it. Or shadcn's `SidebarTrigger` in the sidebar header. The ContentSlot's ResizeObserver re-measures every frame of the collapse/expand transition, so the website follows.
- Downloads: the footer's download button opens the list (`bottom-actions/downloads.tsx`, a popover above the footer inside the sidebar's width): a bar while one runs, the name opens a finished one, the folder button shows it in Explorer, × cancels; a still dot on the button while something downloads; toasts for finished and failed; a spinner while the size is unknown, a bar once it is.
- Load meter: "Ezel is carrying ~N MB" in the footer between the actions (`bottom-actions/load-meter.tsx`), "Ezel is resting" with nothing loaded. The widget polls `get_memory` every 4s only while the sidebar is docked or peeking and the window is visible (`use-load-meter.ts`), never two calls at once; the number eases between readings. Its tooltip lists the heaviest tabs, the shared part and the resting count.
- Features (`features/app-sidebar/`): `context-menu` (the sidebar background's menu, around the sidebar body; which areas get menus and how they behave: `docs/design/context-menus.md`), `navigation`, `swatches`, `space-switcher`, `folders`, `temp-tabs`, `bottom-actions`. They render backend state the widget passes down as props (see Sidebar data flow).
- Scrolling: the sidebar body uses `ScrollArea` (`shared/components/scroll-area`): native scrolling with a trackless, auto-hiding, elastic pill thumb. Use it for any scrollable app UI.
- Shared: `shared/components/{tab-row,favicon,scroll-area}` (`TabRow` is a `SidebarMenuButton`), `shared/types` (all contract data: `TabsState`, `Space`, `SpaceItem`, `Folder`, `Tab`, `Swatch`, `TabLocation`, `PageChanged`, `WindowRadius`), `shared/motion.ts` (`PEEK_TRANSITION` = the titlebar peek's 150ms ease-in-out; use `INSTANT` under `useReducedMotion`).
- **Menus stay in the sidebar**: right-click menus use `SidebarMenuPopup` / `SidebarMenuSubPopup` (`shared/components`), never shadcn's `ContextMenuContent` directly: the sidebar card is their collision boundary.
- **Popups over the page**: the native website webview is drawn on top of the UI. Open popups (menus, submenus, popovers: anything shadcn/Base UI portals out of `#root` with a `data-slot` ending in `-content`) are cut out of it automatically by `usePopupCutouts()` (mounted in `AppLayout`), so they stay visible over the page. Rust keeps every hole until it's cleared, so popup holes reuse ids `popup-0`…`popup-7` and the hook clears them all on mount (a UI reload with a popup open otherwise left a black box over the page). A popup that reaches over the page (overlaps the ContentSlot, `data-slot="content-slot"`, and isn't wholly inside the sidebar card) skips its own open/close animation, since a hole can't fade: it shows and hides in one piece. Popups wholly inside the sidebar keep their fade. Still prefer `side`/`align` that keep them inside the sidebar; anything drawn outside a popup's box (shadows) is clipped over the page.
- **Popups and the page**: clicks on the page never reach the UI, so the UI losing focus closes every open popup (`useDismissPopupsOnBlur`, `shared/outside-press.ts`, mounted in `AppLayout`). A popup opened from the peeking sidebar keeps it out until the popup closes (Zen's `has-popup-menu`). Click inside the sidebar closes only the popup; a click on the page closes both.

### Sidebar data flow
- **Bindings**: every backend call goes through the generated `shared/bindings.ts`: `commands.<camelCase>` (`activate_tab` → `commands.activateTab`, resolving to `{ status, data | error }`; pass it to `unwrap(action, …)` from `shared/report-error`) and `events.<camelCase>.listen` (`events.tabsChanged`, …). Nothing else imports `@tauri-apps/api/core` or `/event` (`grep -rn "@tauri-apps/api/core\|@tauri-apps/api/event" src` matches only `bindings.ts`); `shared/types` re-exports its data types; Tauri window APIs live in `shared/window.ts`.
- **Store**: `useTabs()` (`shared/tabs-store.ts`) is a read-only mirror of the backend: `get_tabs` on first subscribe, then `tabs-changed` replaces the whole state and `tab-updated` patches one tab. `null` until the first snapshot. The UI never keeps its own copy of tab, folder or space data and never updates it optimistically: actions are commands, and the result comes back through the event.
- **Widget → features**: `widgets/app-sidebar` reads `useTabs()` and the page (`get_page`/`page-changed`) and passes data and command wrappers to the features as props; features never import each other. Active highlight = `activeTabId`/`activeSpaceId`; folder open state = `folder.collapsed` (`set_folder_collapsed`); unloaded tabs (`!isLoaded`) show dimmed; `TabRow`'s close button shows on row hover. While a tab plays sound or is muted, a speaker button sits at the row's end (waves breathe while playing, crossed when muted; click toggles `set_tab_muted`) and steps left on hover for the close button. Each row's item is `group/tab`, so its own hover works inside folders. Dev tabs (`isDev`) carry a small mono "dev" chip after the title.
- **No URL bar**: the tab's name is the address field. Double-click a row (or its menu's "Change URL…") and the name becomes the URL in a plain text field (no border, background or ring); Enter navigates the shown tab (the widget selects the tab first) and the name returns; Escape or leaving the field cancels. New Tab (row, `+` menu, sidebar menu, Ctrl+T) opens the command palette, never a blank page; the tab menu's "New Tab Below" still uses `open_tab()` then the new row's field. The widget holds the editing state; `TabRow` draws it. Loading shows as a spinner in place of the row's favicon. Back/forward/reload act on the shown tab and follow it through `page-changed`.
- **Tab menu**: right-click a tab row or swatch (`TabContextMenu`, `shared/components`). The widget builds the items (`widgets/app-sidebar/tab-menu.ts`); browser-standard items only, see `docs/design/context-menus.md`, "Tab menu". List rows take one `TabRowActions` prop (select, close, menu, editing, drag state). New space = `create_space("Space N", next of NEW_SPACE_ICONS)` → `switch_space` → inline rename (also: double-click the active space pill). Space icons are lucide names mapped in `shared/space-icons.ts` (unknown → `Layers`).
- Only ContentSlot calls `set_content_bounds`.

### Tab drag and drop
Zen's behaviour, rebuilt on dnd-kit (HTML5 drag events are swallowed by Tauri on Windows); study and rules in `docs/design/drag-and-drop.md`.
- Folders take drops: the middle of a folder's row drops into it, its edges beside it, and between its open tabs (`folderRow`, `folderTabs`, `FOLDER_TAB_ROW` in `shared/tab-dnd.ts`; target `{ kind: "folder", folderId, gap | null }`).
- `DndContext` lives in `widgets/app-sidebar` (`use-tab-drag.ts`: sensors, target resolution, space switching, cancelling; `tab-drag-preview.tsx`: the pointer-following preview). Features only register draggables/drop zones through `shared/tab-dnd.ts` (`useTabDraggable`, `useTabDropZone`, `DROP_ROW`) and draw the indicator the widget passes them (`DraggableTabItem`, `DropIndicator`).
- A drop calls `commands.moveTab` (`shared/bindings`); the dragged tab stays hidden/dimmed where it was until the next state arrives. No optimistic copy.
- The pointer leaving the sidebar card cancels the drag (the website webview above the UI eats pointer events); on `mouseleave` the real cursor position decides. Never cancel on focus changes: new tab webviews take focus.
- dnd-kit fills `active.rect` only after `onDragStart`; measure the source with `tabDragNode(id)` instead.

### Rules for the tabs step
- The top grid is called **Swatches** (max 8). It shows only the swatches there are (no empty slots), in slot order; it's hidden while there are none. Tabs join by "Add to Swatches" or by dragging onto the grid once it has some.
- Temp tabs and pinned tabs both survive an app restart.
- Closing a temp tab removes it immediately.
- Closing a pinned tab only unloads the site; the pinned tab stays in its space and can be reopened.
- Trash-all clears temp tabs only (they go on the closed-tab stack, so Ctrl+Shift+T brings them back one by one).

## Command palette
Ezel's address bar and quick switcher (Arc's command bar, Zen's floating new-tab URL bar): `widgets/command-palette`, opened from anywhere with `openCommandPalette(target)` (`shared/command-palette.ts`). Design: `docs/design/decisions.md`, "Command palette".
- Targets: `new-tab` (New Tab, Ctrl+T: blank; the result is `open_tab(input)`) and `current-tab` (Ctrl+L or Ctrl+K: holds the shown tab's URL, selected; Enter `navigate`s the shown tab, Shift+Enter opens a new tab instead). Escape or a click on the page closes it without creating anything.
- Recently closed: with nothing typed, the last few closed tabs show as chips under the list (`features/command-palette/recently-closed`); a click is `reopen_recent_tab(n)`.
- Rows: open the typed address (favicon from Google's favicon service) and a Google search (always offered; passes an explicit search URL), "Switch to Tab" across every space and the Swatches, then actions found by name (Copy Link, Reload, Back/Forward, Squint Lens, Greyscale Lens, Toggle Sidebar, Close Temporary Tabs, Go to <space>). Empty new tab: Swatches as tiles plus the space's tabs. `widgets/command-palette/address.ts` mirrors Rust's `resolve_input` so the first row says what Enter does.
- Autofill completes open tabs' hosts (Tab/→ accepts, Backspace removes); Ctrl+Enter turns a word into `www.<word>.com`.
- Built on shadcn `Command` (cmdk, `shouldFilter={false}`: the widget ranks) inside Base UI's `Dialog`, composed at the call site with **no backdrop** (it would dim the UI but not the page). The popup keeps `data-slot="dialog-content"`, so `usePopupCutouts` cuts it out of the website.

## Hotkeys
Every app shortcut is in `shared/hotkeys.ts` (`HOTKEYS`: id, label, default keys (one combination or several), `focusUi`, `whileLoading`). A future Settings page rebinds them there; never hard-code a key check elsewhere. What the browser shortcuts do is in `shared/browser-hotkeys.ts` (`useBrowserHotkeys`, mounted in `AppLayout`).
- Components call `useHotkey(id, handler)`. `useHotkeys()` (mounted once in `AppLayout`) dispatches both paths: the UI's `keydown`, and `hotkey-pressed` from Rust for keys pressed in the website (tab webviews have no IPC, so the UI never sees those keys otherwise). It sends the whole list to Rust with `set_forwarded_hotkeys`; resend it after a rebinding.
- `focusUi: true` for shortcuts that open something to type in (the palette): Rust moves keyboard focus to `ui`. `false` leaves focus in the page.
- Ctrl+B is also shadcn's own sidebar shortcut in the UI (`builtIn`), so its key can't be rebound yet.
- `whileLoading` (Esc): Rust catches it only while the shown page loads, so websites keep Esc for their own dialogs; in the UI it runs only when nothing there wants it (no field focused, no popup open, not already handled) and is never `preventDefault`ed.
- Current (ids in brackets):
  - Ctrl+T new tab palette (`newTab`), Ctrl+L change address (`editAddress`), Ctrl+K the same palette on the shown tab, for commands (`commandPalette`; Chrome's Ctrl+K), Ctrl+B toggle sidebar (`toggleSidebar`)
  - Ctrl+W close the shown tab (`closeTab`; pinned tabs and swatches unload, like their close button)
  - Ctrl+Tab / Ctrl+Shift+Tab recent tabs of the space (`nextTab` / `previousTab`, `cycle_tab`)
  - Ctrl+1…8 the n-th swatch as the grid shows it (`swatch1`…`swatch8`); Ctrl+9 the space's bottom row (`lastTab`)
  - Ctrl+R or F5 reload (`reload`), Ctrl+Shift+R reload without cache (`hardReload`)
  - Alt+← / Alt+→ back / forward (`back` / `forward`), Esc stop loading (`stopLoading`, `whileLoading`)
  - F12 or Ctrl+Shift+I the page's DevTools (`devTools`)
  - Ctrl+Shift+C copy the page's link with a toast (`copyUrl`; the page keeps focus)
  - Ctrl+F find in page (`find`, focuses the UI)
  - Ctrl+D pin the shown tab (`pinTab`; Ezel's bookmark: a temp tab goes to the end of its space's pinned list, a kept one says so)
  - Ctrl+Shift+T reopen the last closed tab (`reopenClosedTab`; also in the sidebar's right-click menu)
  - Ctrl+Alt+S Squint lens, Ctrl+Alt+G Greyscale lens (`squint` / `greyscale`; also palette actions)
- These also act while the UI has focus: Ctrl+R/F5 reload the page, not the UI, and F12 opens the page's DevTools (the UI's own DevTools: right-click › Inspect in a debug build).
- **Toasts**: `showToast({ title, detail?, tone? })` (`shared/toast.ts`), drawn by `Toaster` (`shared/components/toast`, mounted in `AppLayout`): one small pill at a time, bottom-left inside the sidebar's width above its footer, cut out of the website while it shows (`useContentCutout("toast")`), 1.8s. Passive confirmations only (HIG feedback.md); a check draws itself for `tone: "done"`.

## Error and crash pages
A failed top-level navigation (WebView2 `NavigationCompleted`, mapped by `webview2::page_error_for`) or a crashed or hung renderer (`ProcessFailed`) sets `Live.error`: the tab's webview hides (`can_show`) and `page-changed.error` makes the UI draw Ezel's own page in its place (`features/browser-view/error-page`: an empty canvas, one sentence, one action: Try Again / Reload, Go Back for certificate errors, Change Address… for not found and certificate). There's no way past a certificate error. Only those statuses get Ezel's page: SmartScreen's warnings, cancelled loads and sign-in prompts stay WebView2's. The next navigation that starts (Try Again is `reload`) clears it.

## HTML fullscreen
A page entering fullscreen (WebView2 `ContainsFullScreenElementChanged`, `Live.fullscreen`) makes the window fullscreen while that tab is shown (`apply_fullscreen`, also on every tab switch) and sets `page-changed.fullscreen`; `AppLayout` then drops the titlebar, the sidebar and the frame's padding and radius, so the page fills the window. Esc (caught in Rust before any other shortcut while the shown page is fullscreen) or the site's button leaves it; the window returns to what it was.

## Theme
`src/theme/`: `ThemeProvider` (in `App.tsx`, `defaultTheme="system"`, no persistence yet; pass `storageKey` to persist) around a framework-agnostic store (`theme-store.ts`).
- Applies shadcn's convention: the `dark` class on `<html>` plus `color-scheme`. **The colours stay shadcn's `:root` / `.dark` variables in `index.css`**; the provider never redefines them.
- Follows the OS live while on "system". Switching disables transitions for one frame so the whole UI doesn't animate.
- `index.html` applies the system theme before first paint (no white flash). Update it if persistence is turned on. Before that, Rust creates the window hidden, gives it and the `ui` webview the system theme's background (`#0a0a0a` dark, white light: index.css `--background`) and shows it once the `ui` webview exists and its resize handler is attached (`build_window`; showing grows the client area, and a missed resize left the UI short of the window's bottom), so launch never flashes white.
- Hooks: `useTheme()` (state + `setTheme` / `setTokens` / `replaceTokens`), `useThemeSelector(fn)` (re-renders only for that slice), `useResolvedTheme()`.
- For the future theme editor: `setTokens({ light: { "--primary": "…" }, dark: { … } })` overrides any index.css variable at runtime through one `<style data-theme-tokens>` (rules `:root:not(.dark)` / `:root.dark` out-rank index.css). No React re-render of the tree is needed to recolour.
